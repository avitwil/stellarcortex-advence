# Decisions log (Defaults rule)

Each entry: ID, decision, one-line reason. Closed spec decisions (D-01..D-25) are not repeated here.

| ID | Decision | Reason |
|---|---|---|
| DL-001 | Chromium in the bot computer comes from Debian stable + security via apt pinning on the Ubuntu 26.04 base. | Ubuntu ships Chromium only as a snap, which cannot run in a container; Debian's build is free and gets security updates. |
| DL-002 | Coding engines are installed into the bot's home volume from npm on first start, never baked into the image. | C-06: nothing proprietary is redistributed, even inside a locally built image. |
| DL-003 | The bot-computer image is always built locally on the operator's machine (FR-PC-07 "builds"), never pushed to a registry. | Keeps C-06 and avoids paid/public registries. |
| DL-004 | VNC inside the container listens on loopback only, with a random per-bot password injected as a Podman secret; noVNC's port is published to host loopback only and reached through the server's authenticated proxy. | Secure by default; no open VNC. |
| DL-005 | TypeScript 5.9 (not 7.x) and Vite 7 / Vitest 3. | Most widely supported by Electron, Capacitor and Vite tooling today. |
| DL-006 | Desktop Google login uses the fixed loopback redirect `http://localhost:47823/oauth/callback`, registered on the operator's Web client; the client forwards code + PKCE verifier to the server, which exchanges it. | Google Web clients do not accept LAN IPs or self-signed hosts as redirects; the server stays the relying party (D-13). |
| DL-007 | Browser UI login (D-16) uses the same loopback redirect; if nothing listens on the browser's machine, the user pastes the redirected URL into the page. | Works without a public domain or paid certificate. |
| DL-008 | Other users are allowlisted by Google email; the `sub` is bound on their first verified login and used as the key from then on. | The owner knows emails, not `sub` values; `email_verified` is required. |
| DL-009 | The server's TLS key is ECDSA P-256 in a self-signed X.509 certificate; clients pin the SHA-256 of its SubjectPublicKeyInfo. | Chromium (Electron/WebView) does not accept Ed25519 TLS certificates. |
| DL-010 | Master key wrapping order: OS keystore (Windows DPAPI, macOS Keychain, Linux Secret Service via `secret-tool`) if usable, else Argon2id passphrase stored in a file outside the data folder (created by the installer, mode 0600). | NFR-SEC-04: a dump of the data folder alone reveals nothing. |
| DL-011 | The TLS private key is sealed with the master key at rest. | It is a secret; NFR-SEC-04. |
| DL-012 | The first device is approved on the server console (`advence pair`); later devices are approved by the owner on a paired device. Approval requires typing the 6-digit code shown on the new device. | There is no owner before the first device; typing the code forces a real comparison. |
| DL-013 | Session tokens: 32 random bytes, stored only as SHA-256, 15 min lifetime; refresh needs a valid device signature from an active device bound to an allowlisted user. | NFR-SEC-03. |
| DL-014 | Request nonces are kept in SQLite for the 60 s skew window, so replays are refused across restarts too. | NFR-SEC-02. |
| DL-015 | Signed WebSocket frames: an `auth` frame within 5 s of connect, then every client frame signed; session expiry requires a fresh `auth` frame on the same socket. | Browsers cannot set headers on WebSocket; NFR-SEC-02/03. |
| DL-016 | Server traffic from the native shells goes through their native layer, which pins the server key: Electron's main process (Node `https`/`ws` with a pinned agent, renderer CSP `connect-src 'self'`), Android's Capacitor plugin (OkHttp). | WebView/renderer pinning is unreliable (Chromium caches certificate verdicts), and the renderer then has no network access at all. |
| DL-017 | Encrypted chat history is searched through an in-memory SQLite FTS5 index rebuilt at start. | A plaintext FTS index on disk would defeat NFR-SEC-04. |
| DL-018 | On a Linux desktop with no keyring (safeStorage backend `basic_text`), the device key file falls back to owner-only permissions. | Linux desktops normally have libsecret/kwallet; refusing would lock those users out. |
| DL-019 | E2E tests that launch Electron as root drop to an unprivileged user; the app always enables Chromium's sandbox. | Chromium refuses its sandbox as root; the product must never disable it. |
| DL-020 | Windows and macOS installer jobs run on demand (`installers` workflow); Linux, tests, image and APK run on every push. | macOS/Windows runner minutes count 10x/2x against the free private-repo quota (C-04). |
| DL-021 | Android release APK is signed only when a keystore is supplied as a CI secret; otherwise it is built unsigned. The debug APK is used for emulator tests. | No keystore may enter the repo; signing keys are the owner's to create. |
| DL-022 | Android ships one universal APK plus per-ABI APKs (arm64-v8a, x86_64), minSdk 28. | FR-CLI-02 asks for Android 9+, arm64 + x86_64; a universal APK is simplest to sideload. |
| DL-023 | Android QR scanning uses the WebView camera (getUserMedia + jsQR) with the CAMERA permission; no extra native scanner. | Reuses the UI scanner; fewer native components. |
| DL-024 | The UI needs a current Android System WebView (Chromium 99+). CI checks Android 9 (API 28) for install, start and page load, and a current image (API 34) for the rendered UI. | Android 9 devices update the WebView through the store; the stock API 28 emulator WebView is never updated and cannot run the bundle. |
| DL-025 | Subscription sign-in: the Claude subscription takes the long-lived token from `claude setup-token` pasted by the owner; the ChatGPT subscription runs the Codex CLI device login in a container. Both are sealed in the secret store and handed to the CLI by environment only. | Both are the CLIs' own official sign-in flows; nothing is stored in a volume. |
| DL-026 | Local model servers and subscription sources are owner-only; OpenAI-compatible APIs with a key must use https. | D-07c limits subscriptions to the owner; a member pointing the server at LAN hosts would be a request-forgery path. |
| DL-027 | Push endpoints are accepted only on the ntfy server the owner configured (or the sidecar's URL). | The server POSTs to registered endpoints, so any other host would be a request-forgery path. |
| DL-028 | Notifications per Bot are "all" or "off", plus one app-wide mute per user. | The fewest settings that cover FR-UI-03 and FR-UI-07 notifications. |
| DL-029 | Group chats: mentioned Bots answer, otherwise the primary (or first) Bot; a Bot's reply that @mentions another Bot hands it the next turn, at most 3 hops. Delegation via the primary Bot's tool nests at most 2 levels. | Bounded hand-offs keep two Bots from talking forever and running up cost. |
| DL-030 | Attachments are uploaded as base64 inside the signed JSON request (25 MB cap). | Every request stays covered by the device signature (NFR-SEC-02) without a second upload protocol. |
| DL-031 | Bot computers use rootless Podman with `--network pasta:--no-map-gw`; the only host ports forwarded in are the owner's local model servers on a loopback address (`-T port`), never the server's own port. Without pasta, slirp4netns with `allow_host_loopback=false` is used and Settings shows the computer as less isolated. | Cuts the container off from host loopback services by default (NFR-SEC-08) while keeping D-07a local models usable from engines. |
| DL-032 | The server drops TCP connections whose local peer socket belongs to a container network helper (pasta, passt, slirp4netns, gvproxy, vpnkit), found through `/proc` on Linux. | User-mode networking reaches the host's LAN address from host sockets, so this is what blocks the API from containers on Linux (NFR-SEC-08); Windows and macOS are a manual check. |
| DL-033 | The live view carries RFB bytes as base64 text frames over our own pinned WebSocket (signed auth frame, session rechecked every 15 s) to the container's websockify on the host loopback; noVNC 1.7.0 (MPL-2.0) is the viewer. | Every client bridge (browser, Electron main process, Android OkHttp) already carries pinned text frames; no second TLS stack or port. |
| DL-034 | Take-over is a server-side lock: while the owner has it, the Bot's computer actions wait; the viewer is view-only otherwise. | FR-UI-05 says the Bot pauses during take-over; enforcing it on the server covers every client. |
| DL-035 | Engines run with their own approval prompts off (Claude Agent SDK `bypassPermissions`, Codex `--dangerously-bypass-approvals-and-sandbox`, OpenCode default) because they run only inside the Bot's isolated container. | The container is the sandbox (D-10, NFR-SEC-08); a nested sandbox would need privileges the container does not have. |
| DL-036 | Bots get the `code` and `computer` tools by default; `host` needs the per-Bot Host control toggle (owner only) as well. | FR-PC-09 makes host control opt-in; the Bot's own computer is safe by isolation. |
| DL-037 | The image tag follows the server version (`localhost/advence-bot-computer:<version>`); a container whose image, limits, forwards or GPU label differs is re-created on the same volume. | Updates (D-24) roll computers forward without losing the home volume (FR-PC-03). |
| DL-038 | Disk limits are enforced by a 5-minute watchdog (`du` of the home volume); over the limit the computer stops and stays stopped until the limit is raised. | Rootless overlay volumes cannot set a hard quota on every filesystem; a watchdog works everywhere (FR-PC-05). |
| DL-039 | `advence computer setup` installs Podman with the OS package manager (apt/dnf/zypper/pacman), Homebrew or winget, otherwise points to podman.io; on Linux it adds sub-IDs, pasta and lingering; on Windows/macOS it creates the Podman machine; then it builds the image. The server starts a stopped Podman machine at boot while auto-start is on. | FR-PC-07 with only free official sources (C-04); every system change is confirmed unless `--yes`. |
| DL-040 | The UI bundle is one script (lazy imports inlined) built for ES2022, and SRI hashes are computed after Vite's last chunk rewrite. | noVNC uses top-level await; one script keeps SRI (D-16) covering all code. |
| DL-041 | The memory vault is one git repo per user at `<dataDir>/vault/<userId>/` (isomorphic-git, MIT), laid out as `agents/<bot>/`, `shared/`, `user/`, `skills/` and `curator/`. | Per-user repos keep one user's history and rollback away from another's; isomorphic-git needs no git binary on the host. |
| DL-042 | Encrypted mode stores each file as `.sealed/<HMAC of path>.bin` (XChaCha20-Poly1305 with the vault key, path as AAD) and seals commit messages too (`advence-sealed:` prefix). Plain mode is owner-only, writes ordinary Markdown, and the warning says versions saved while plain stay readable in git history after switching back. | D-15 encryption at rest without leaking note names through paths or commit messages; rewriting history on every switch would break rollback (FR-MEM-04). |
| DL-043 | Retrieval is an in-memory FTS5 table rebuilt from the vault, ranked by bm25 with weights title 6, tags 3, body 1; embeddings are not built (off by default per FR-MEM-03). | No plaintext index on disk; title and tag hits are the strongest signal for short notes. |
| DL-044 | Write guard limits: note names up to 80 chars, notes up to 20 000 chars, skill bodies under 500 lines, duplicates at Jaccard word similarity ≥ 0.85, a do-not-capture list of secret patterns (keys, tokens, private keys, passwords) and third-party emails and phone numbers. Every rejection is an activity entry. | FR-LRN-02 rules with fixed, testable thresholds. |
| DL-045 | The learn pass runs after a reply that used a task tool (`code`, `computer`, `host`, `delegate`, `skill_run`), after a reply to a message that looks like a correction (English and Hebrew patterns), or every 10 user turns or 10 tool iterations; it runs the Bot's own model in the background with memory and skill tools only and posts nothing to chat. | FR-LRN-01 triggers without a second model source or extra cost settings. |
| DL-046 | Skill metadata and review records are sealed in SQLite (`skills`, `skill_reviews`), with an HMAC of the name for uniqueness; skill files live in the vault (`agents/<bot>/skills/<name>/` for Bot skills, `skills/<name>/` for installed ones, `archive/` for archived). | Telemetry and status need fast queries; contents stay encrypted like the rest of the vault. |
| DL-047 | Installs accept GitHub `owner/repo[/path][@ref]` and tree URLs, `skills.sh/<owner>/<repo>/<skill>` (resolved to GitHub) and local absolute folders. Downloads come from codeload at the resolved commit SHA; limits are 25 MB tarball, 200 files, 512 KB per file, 5 MB total; links and binary files are skipped. | FR-SKL-01/02 with the fewest moving parts: one HTTPS host per source and no git binary. |
| DL-048 | Each user approves installs for their own Bots; local folders are the server owner's only, because they read the host filesystem. Bots have no install tool. | FR-SKL-02 "owner approves" applied per account; local paths would otherwise let a member read host files. |
| DL-049 | Third-party skill scripts run with `skill_run`, which copies the skill's files into the Bot's computer and runs them there as the Bot user; when the computer is unavailable the tool fails instead of running on the host. | FR-SKL-03 with the same isolation as every other Bot command (NFR-SEC-08). |
| DL-050 | The curator ticks hourly and runs at most weekly while no Bot is replying; its ledger is `curator/ledger.jsonl` in the vault, each run snapshots the vault commit and skill states, and dry-run, run and rollback are in Settings → Skills and `POST /v1/skills/curator/*`. Archiving moves the folder, nothing is deleted. | FR-LRN-05 commands exposed where the owner already manages skills; the vault's git history doubles as the snapshot store. |
| DL-051 | Consolidation (off by default, `memory.consolidation`) merges two skills of the same Bot whose bodies are at least 0.5 similar, using that Bot's model; the older skill keeps its name and the newer one is archived into it. | FR-LRN-06 with a deterministic merge direction and the curator's rollback. |
| DL-052 | CI validates exported skills with `skills-ref` 0.1.1 (Apache-2.0) run through `pipx`; it is a CI tool, not shipped. | FR-LRN-03 names `skills-ref validate` as the acceptance check. |
| DL-053 | `yaml` 2.9.1 (ISC) parses and writes SKILL.md frontmatter, and is pinned at the workspace root as well. | One YAML parser across packages keeps a single Vite instance for the UI typecheck. |
| DL-054 | Bot computers drop every capability except `CAP_SYS_CHROOT`. | Chromium's namespace sandbox cannot start its zygote without it (seen in rootless CI and reproduced locally); with no-new-privileges and no other capability, chroot alone gives no way out of the container, and it keeps FR-PC-04 without `--no-sandbox`. |
| DL-055 | MCP uses the official TypeScript SDK 2.4.0 (`@modelcontextprotocol/client` and `/server`, MIT) with version negotiation `auto`: `server/discover` first (2026-07-28), and `initialize` with sessions when a server does not answer it (2025-11-25). Task results are moved into `_meta['advence/task']` at the transport so the SDK's tool call accepts them. | One maintained client for both spec eras (FR-MCP-02); the SDK rejects a task result type in `callTool`, and lifting it at the transport keeps the rest of the SDK unchanged. |
| DL-056 | Members can add only `https` servers on public addresses: the name is checked when added, and every connection resolves it and refuses it if any address is loopback, private, link-local, shared, documentation or multicast (IPv4-mapped forms included), then connects to the address it checked; redirects are not followed. Only the owner can add `stdio` commands and private addresses. Every `stdio` server runs inside the Bot's computer, never on the host. | A member must not reach the host, the LAN or a cloud metadata service through the server (SSRF, DNS rebinding), and local commands must keep NFR-SEC-08 isolation. |
| DL-057 | MCP sign-in is OAuth 2.1 with PKCE, `resource` (RFC 8707) and `iss` checks (RFC 9207), on the desktop through the loopback redirect and elsewhere by pasting the address the browser lands on. Client registration order: pre-registered client if set, else the owner's Client ID Metadata Document if set and supported, else dynamic registration. After 3 sign-ins in a row that do not lead to a working call, the server is marked failed. | The spec's preferred order with no hosted service of our own; the limit stops sign-in loops against a server that keeps asking for more scopes. |
| DL-058 | This server's own MCP endpoint is `/mcp` on the TLS port, open to owner access tokens only (stored as hashes, shown once); requests with an `Origin` header are refused; external clients trust the self-signed certificate through `NODE_EXTRA_CA_CERTS`. | FR-MCP-04 with owner auth, no browser access (DNS rebinding) and no change to the pinned-certificate model. |
| DL-059 | Google connections assume Testing mode: refresh tokens are treated as ending 7 days after consent, a reminder goes out on day 6, and the connector shows "reconnect" afterwards. Scopes are `gmail.modify`, `gmail.send`, `calendar.events`, `drive.readonly`, `drive.file` and `contacts.readonly`. Android asks for the same consent through Google's authorization client (`play-services-auth`, Android SDK License) and the server exchanges its server auth code. A new consent replaces the stored refresh token without revoking the old one; only Disconnect revokes. | Testing mode is the free path for a personal Google project; these are the least scopes that cover every FR-GGL-06 tool; the Android client is Google's supported way to get offline access on a phone; Google's revocation ends the whole grant, so revoking on re-consent would end the new token too. |
| DL-060 | Prompt-injection taint (NFR-SEC-11) has three levels per reply: `none`, `work` (seen on a work surface: the Bot's computer, its coding engine and skill files, or the host desktop) and `outside` (Google read tools, every MCP tool and meta tool, trigger payloads, memory notes and skills marked tainted, and any message stored as tainted). For a Bot that is not autonomous, a call is held when it is not read-only and the taint is `outside`, or the taint is `work` and the call is not on the same single surface the content was seen on. The rule runs in the runtime's tool loop, not in the prompt. | FR-PRO-07 requires a hard block. Holding only actions (reads still run) keeps chat useful; the surface rule lets a user-directed coding or computer task continue, while content seen in the Bot's computer can never reach mail, MCP, Google, the host desktop or any other tool. |
| DL-061 | A held call becomes an approval card showing the exact tool and input; "Allow" runs that one call as it was made and the Bot continues, "Don't allow" tells the Bot. The decision is logged. | The user stays in control without the Bot being able to rephrase what runs. |
| DL-062 | Autonomous means the Bot's "Proactive" toggle is on, the Bot is not paused and the user has not paused all proactivity; it is checked again before every tool call against the Bot's current state. Routines and suggestions run only for autonomous Bots; a trigger for any other Bot is recorded as `skipped` and never reaches its model. | FR-PRO-03 gives full autonomy to proactive Bots only; FR-PRO-07 keeps the old rule for the rest; re-checking per call makes a pause effective before the next action (FR-PRO-06). |
| DL-063 | The kill switch is per user (`proactive.paused:<user>`) plus a per-Bot `paused` flag. Pausing aborts running autonomous runs at once and drops queued ones (status `stopped`). | FR-PRO-06 names a global button; each user controls only their own Bots. Aborting the request is what makes the 2-second bound hold. |
| DL-064 | New mail is found by polling Gmail every 60 s (`in:inbox newer_than:2d` plus the routine's filter); the first check only learns what is already there. Calendar, Drive and Bot-computer watchers poll on the same cycle; MCP notifications use `subscriptions/listen` (2026-07-28) or `resources/subscribe` (2025-11-25) with a 10 s debounce. | Gmail push needs a public Pub/Sub endpoint and a paid-tier setup; polling is free and works behind NAT (C-04). |
| DL-065 | Schedules are five-field cron expressions evaluated in the routine's time zone with `Intl`; a daily digest is a schedule at HH:MM whose run gets the activity log since the last digest. Due routines are checked every 15 s. | No extra dependency; time zones and daylight saving come from the platform's ICU data. |
| DL-066 | Webhook routines get a secret address `/v1/hooks/<routine>/<secret>` (24 random bytes, stored as a hash, shown once). The route needs no session, is rate limited per IP and per routine, takes bodies up to 64 KB and hands the body to the Bot as outside content. | External services cannot sign our device requests; a capability URL is the simplest secure option. |
| DL-067 | Runs are queued and each Bot runs one at a time; a run posts the routine's instructions and the trigger data as a system message in the Bot's direct chat and replies there, so the run history links to that output. Runs in flight when the server stops are marked `stopped` (`interrupted`). | One place for output; no parallel runs fighting over one Bot's computer. |
| DL-068 | Suggestion cards come from a `suggest` tool that only autonomous Bots get (title, detail, the full task, rank 1 to 5). "Do it" queues the task as an autonomous run of that Bot. | FR-PRO-04: cards are ranked and run start to finish with one tap; only Bots allowed to act on their own may offer to. |
| DL-069 | Memory notes and skills written while the writer's context held outside or work content are marked (`tainted_items`). Marked notes and skills are left out of every Bot's prompt, and reading one (memory_read, memory_search, skill_view, skill_run) taints the reader as outside. The learn pass marks what it saves from a chat that held outside content. | Without it, a proactive Bot could pass injected text through shared memory into a Bot that is not proactive. |
