# Phase P7: Hardening and release

Exit criterion (section 8): "Fresh install on 3 OSes + Android; signed release candidate ready.
The owner approves before anything is published (C-07)."
Scope: NFR-*, FR-CLI-01, 02, 05, 06, D-24, docs.

## What was built
- **One-line server install (FR-CLI-06):**
  - `install/install.sh` (Linux and macOS) and `install/install.ps1` (Windows), rendered with the
    feed address and the pinned release keys by `scripts/release/render-installers.mjs`.
  - Each one downloads Node.js from nodejs.org and checks it against nodejs.org's SHA-256 list.
    It then downloads the server bundle and checks the manifest signature, the bundle's SHA-256
    and its size before anything is extracted. Any failure stops the install with nothing
    installed.
  - It installs the launcher and a service that starts at boot: a systemd user unit with
    lingering, a launchd agent, or a scheduled task at sign-in (DL-079). It adds the `advence`
    command, runs `advence computer setup --yes` (Podman from the OS packages, rootless mode and a
    locally built Bot computer image), waits for the server to report healthy and shows the
    pairing QR code.
- **Server updates with rollback (FR-CLI-05, NFR-REL-02, D-24):**
  - The server checks the feed daily. The owner installs from **Settings → Updates** or with
    `advence update apply` (DL-072).
  - The update is downloaded with a size limit and hashed as it streams, checked against the
    signed manifest, extracted into a staging folder and moved into `versions/<v>/`.
  - The launcher copies the database, starts the new version and waits for its health report.
    When it does not come within two minutes, the launcher restores the database, removes the
    failed version and starts the previous one; the Updates page shows what happened (DL-070).
  - An update that needs another Node.js major version is refused and asks for the installer
    (DL-074). Feeds must be https, except on loopback (DL-076).
- **Desktop updates (FR-CLI-05):** electron-updater downloads from the self-hosted feed. Before
  anything installs, the app checks the signed manifest, the version and the installer's SHA-256
  and size. Windows and Linux install on quit; macOS opens the verified DMG (DL-071).
- **Android updates (FR-CLI-05):** **Settings → Updates** checks the signed manifest; the native
  plugin downloads the APK only from the feed built into the app, checks its hash and size, and
  opens the system installer. Android itself requires the same signing certificate (DL-077).
- **Release tooling (NFR-SEC-10):**
  - `scripts/release/keygen.mjs` writes the Ed25519 release key outside the repository with
    owner-only permissions.
  - `bundle-server.mjs`, `manifest.mjs`, `sign.mjs` and `verify.mjs` build, describe, sign and
    check a release. Several pinned keys allow key rotation.
  - The `release-candidate` workflow (run by hand) builds every bundle, installer and APK, writes
    and signs the manifests when the key is a secret, verifies them against the pinned key and
    keeps a private `feed-<version>` artifact. Nothing is published, tagged or released by CI.
- **Hardening tests:**
  - first streamed token under 1 s (NFR-PERF-01);
  - ten Bots answering at once (NFR-PERF-02);
  - kill and restart with chats, computers, missed schedules and webhooks resuming (NFR-REL-01);
  - axe on every main screen and every Settings section in English and Hebrew (NFR-A11Y-01,
    DL-080);
  - the cost audit of every outside host (NFR-COST-01, DL-081).
- **Docs:** `README.md`, `docs/user-guide.md`, `docs/admin-guide.md`, `docs/release.md`,
  `docs/cost-audit.md`.

## Review
A correctness and appsec review covered the server updater and its routes, the launcher, the
release scripts, both installers, the desktop and Android updaters, and the three workflows.

Checked and found sound:
- every update route is owner only on the server, not just in the UI;
- the server checks the signature before it parses the manifest, refuses an older or equal
  version, another platform and another Node.js major, and never follows redirects;
- the installers validate the feed address and keys before they are written into the scripts,
  and no feed data reaches a shell or PowerShell command;
- workflow inputs pass through `env` and are validated, and the release key is never printed;
- the Android plugin downloads only from the feed built into the app, with redirects off, a size
  cap and a native hash check, and its file provider is not exported.

Fixed during the review:
- **Desktop install on quit (high):** electron-updater would install whatever it downloaded
  last, which a feed attacker could swap after a genuine update had been verified. The app now
  installs only the file it verified, hashes it again first, and stops downloading once a
  verified update is waiting (DL-083). This also makes install on quit work at all.
- **Installer order:** a new Node.js replaced the installed one before the release was verified.
  It is now unpacked in a temporary folder and swapped in only after verification (DL-082).
- **Downgrades and upgrades by installer:** a re-run installed any signed release, older ones
  included, and switched without a backup or a health check. Older releases are now refused, and
  an upgrade goes through the launcher's backup, health check and rollback (DL-082).
- **Launcher killed during a trial:** the next start overwrote the pre-update database backup
  with the already migrated database. A trial marker now makes the next start roll back at once
  and keeps the original backup.
- **Unbounded reads:** the manifest reads on the server and in the desktop app buffered a
  response without a length before checking its size. They now stop at the limit, with a
  timeout on the desktop too.
- **Concurrent updates:** two applies (app and shell) shared fixed download and staging paths.
  Each job now has its own folder, and the file is hashed again right before it is extracted.
- **Pre-release order:** `1.0.0-rc.10` sorted below `rc.9`. Versions now follow semver order.
- **Plain http:** a host name such as `127.evil.example` counted as loopback, and the installer
  followed redirects from https to http. Only literal loopback addresses count now, and curl may
  use http only for a loopback feed.
- **Android file provider:** narrowed from the whole cache and external storage to the updates
  folder.
- **Release key in CI:** the signing job now runs in a protected `release` environment, so a
  workflow pushed to another branch cannot read the key (DL-084).
- **UI (found in CI):** the Google connection card floated over the Send button. The card tray
  now sits above the composer.

Known limit: a feed that is taken over can keep serving the last signed release, which holds back
updates but cannot install anything unsigned (DL-085).

## Owner steps before a release
1. Create the release key on your own computer and set `ADVENCE_RELEASE_PUBKEY`,
   `ADVENCE_FEED_URL` and `ADVENCE_ANDROID_SHA1` as repository variables (`docs/release.md`).
2. Optionally add the `ADVENCE_RELEASE_KEY` secret and the Android keystore secrets.
3. Run **Actions → release-candidate**, check and sign it, and test it (MC-P7-*).
4. Approve and upload the feed folder to your server (C-07).
